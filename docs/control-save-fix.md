# Сохранение контрольной при отправке

Правка от 4 октября 2026 года. Изменены `control/control_core.js` и `control/control.html`; добавлен `tests/control_submission.test.js`.

При первой отправке сохраняется неизменяемый снимок payload и ключ повторной передачи. При сетевой ошибке, таймауте или ответе без подтверждения черновик остаётся на устройстве. После перезагрузки повтор использует тот же payload, включая время создания, и тот же ключ. Для назначений заголовок `Idempotency-Key` сохраняет существующий контракт API.

Подтверждением назначения считается непустой строковый `submissionId` в успешном ответе без признака ошибки. Получение оценки проверяется отдельно: отсутствие, null, пустая строка, отрицательные баллы или баллы выше максимума не превращаются в нулевую оценку. При наличии номера записи работа помечается принятой даже без оценки; повторная отправка блокируется. В старом режиме без назначения сохраняется совместимость с ответом, содержащим корректную серверную оценку без ID.

После успешной отправки ответы и квитанция остаются в одной локальной записи. Новый ключ хранения различает назначения одного варианта. Для старого черновика, у которого назначение неизвестно, предлагается явное восстановление; исходная запись не удаляется. Авторизованный сброс предварительно сохраняет предыдущую работу в локальный архив, а новая попытка получает новый ключ передачи. Сброс во время отправки и повторный одновременный запрос заблокированы.

Если локальное хранилище не принимает запись до отправки, POST не выполняется и ученик получает сообщение о невозможности сохранить резервную копию. Если сохранение квитанции не удалось после серверного приёма, принятая работа остаётся заблокированной от повторной отправки в текущей вкладке; показывается предупреждение. При перезагрузке остаётся прежний сохранённый ключ запроса. Обработка повторов на сервере требует поддержки существующего `Idempotency-Key`.

Проверка: 19 автоматических проверок, включая прежние проверки навигации, публичных ссылок и деепричастий. Новые сценарии охватывают принятую работу, отсутствие и некорректность оценки, сетевую ошибку, точный повтор после перезагрузки, двойное нажатие, сбой хранилища, сброс, архив и восстановление старого черновика. В Edge дополнительно проверены три сценария на подменённом API: успешная сдача, принятая работа без оценки, разрыв соединения с повтором после перезагрузки. Проверено отображение на ширине 390 px.

С настоящим API Yandex Cloud проверена локальная исправленная форма: тестовая работа с 10 ответами сохранилась после перезагрузки, сервер принял первую отправку, а после намеренной потери подтверждения повтор вернул прежний ID с признаком duplicate. Чтением YDB подтверждены одна запись и одна использованная попытка. Исходный файл в Object Storage совпал с отправленным payload и контрольной суммой. Пользователь открыл тестовую запись в кабинете учителя и сохранил ручную проверку; итог 14 из 15 подтверждён отдельным чтением базы. Тестовая работа явно помечена «ТЕСТ».

Ограничения: backend находится в отдельном проекте. Причина наблюдавшейся ошибки 502 была устранена отдельно запуском остановленной базы YDB; изменение фронтенда само по себе не восстанавливает недоступный сервер. Отдельного API получения задержавшейся оценки в клиентском контракте не обнаружено, поэтому автоматический запрос такой оценки не добавлен. Загрузка самой страницы контрольной после перезагрузки по-прежнему требует доступного API, хотя сохранённые ответы не удаляются при его недоступности. Изоляция по профилям разных учеников, перенос между устройствами и серверное автосохранение относятся к следующему этапу общей модели. В старом режиме без назначения клиент не может гарантировать серверное устранение дублей при потере ответа: контракт заголовков этого endpoint не расширялся.
